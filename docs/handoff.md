## Ревью Select: что нашли и как починили

Человек проверил скриншот открытой панели Select и указал на две проблемы с размерами — обе
оказались реальными багами, не только в Figma, но и в коде:

1. **Подсветка пункта росла по тексту (Hug), а не на всю ширину панели (Fill).** В коде
   `SelectItem` уже был `w-full` — там было ок. В Figma пункты были нарисованы `Hug`-ширины
   в каждом варианте по отдельности.
2. **Панель была шире поля и выступала справа.** Причина в коде: `SelectContent` брал
   Radix-дефолт `position="item-aligned"` + жёсткий `align="center"` — панель выравнивалась
   по выделенному пункту, а не по краям триггера (`min-w-(--radix-select-trigger-width)` на
   `Viewport` реально работает только при `position="popper"`). Переключил дефолт на `popper`,
   убрал принудительный `align`.
3. Чтобы правило 1 не повторилось у будущих компонентов со списками (menu item, command item) —
   выделил **`Select / Item`**: отдельный Figma-компонент, пока локальный для Select
   (`State`-variant default/highlighted/disabled; `Text` TEXT; `Selected` BOOLEAN — чек-марк
   переключается видимостью дочернего инстанса, не вариантом, поэтому 3 нарисованных варианта
   дают 6 видимых комбинаций). Панель `State=open` собрана из его инстансов, `Fill`-ширина.
4. Два новых правила `npm run figma:layout`: дочерние элементы списка — Fill, не Hug;
   повторяющиеся элементы внутри компонента — экземпляры, не нарисованные слои. Прогнаны по
   всем 54 компонентам. Второе правило поймало ещё и **Input OTP** (его 4 слота были нарисованы
   как frame в каждом из 4 состояний = 16 копий) — не стал оставлять новое правило красным для
   уже сданного компонента, выделил **`Input OTP / Slot`** так же и заменил все 16.
5. В `shadcn-mapping.md` — пометка: при переносе группы 4 (Dropdown Menu, Context Menu,
   Command) сравнить их пункты с `Select / Item` и решить, выносить ли общую основу в
   `Menu / Item`.

**Бонус-находка во время этого ревью:** `ownerName()` в `figma-layout-export.js` резолвила
владельца исключения (`EXEMPT_FIXED_WIDTH`/`EXEMPT_NAKED_TEXT`) по имени **варианта**
(`v.name`, вида `Size=md, State=default`), а не корневого компонента — молча ломало
сопоставление ключей для Input/Textarea/Native Select. Расхождение маскировалось тем, что
закоммиченный `figma/layout.json` не пересобирался после более раннего рефакторинга
`ownerName` (тот рефакторинг чинил другой кейс — Field с вложенным инстансом Input — и чинил
верно). Починил, задокументировал в SKILL.md → «Топ ловушек» → пункт 8.

## Вопрос человека: почему проверка свежести снимка не поймала баг `ownerName`

Хеш-сверка (`use_figma`-ответ vs `node scripts/figma-layout-check.mjs --hash`) проверяет
**данные снимка против текущей Figma** — вручную, `npm run verify` в Figma не ходит. Баг
`ownerName` был правкой **логики самого экспортёра**, а не Figma-состояния — снимок данных при
этом физически не менялся, оба хеша совпадали. Процесс требовал пересборки «после правки
раскладки», но не «после правки самого экспортёра».

Закрыл для этого конкретного класса дыр (`a5378b3`): `scripts/figma-layout-save.mjs` —
обязательная точка сохранения снимка, проставляет `exporterHash` (хеш текущего
`figma-layout-export.js`) в `figma/layout.json`; `figma-layout-check.mjs` сверяет его с файлом
на диске при каждом запуске и падает (exit 2), если экспортёр менялся после снимка. Проверено
и позитивным, и негативным сценарием. **Дыра для дрейфа самой Figma** (кто-то поправил
компонент и не переснял) остаётся ручной — без живого похода в Figma из `npm run verify` это
не автоматизировать; не стал изображать, будто автоматизировал.

## Порталы (общее правило, не разовый фикс)

Radix `Portal` рендерит контент (`SelectContent` и далее любой оверлей) в `document.body`, вне
DOM-дерева своей обёртки — локальный `data-brand`/`dark` (в том числе в `BrandMatrix`) до него
не доходит, действует только `<html>` (глобальный тулбар Storybook). Обёртка над любым
Radix-примитивом с порталом принимает проп `container`, передаёт в `…Primitive.Portal`;
`BrandMatrix` даёт свою ячейку как `container` через `ref`/`useState`. Задокументировано как
общее правило (не только для Select): `code.md` → «Как переключаются бренд и тема» (с кодовым
шаблоном) и SKILL.md → «Топ ловушек» → пункт 9 — чтобы Popover/Dropdown Menu/Dialog в группе 4
делали так же с самого начала, без повторного открытия этой проблемы.

## Линтер `var(--x)`

`npm run tokens:check` теперь сверяет каждую `var(--x)` / Tailwind v4 shorthand `util-(--x)` в
компонентах с реально объявленными переменными в `tokens.css` — опечатка в имени токена раньше
тихо падала на дефолт Tailwind и ловилась только глазами на скриншоте (если вообще ловилась).
`--radix-*`/`--anchor-*` явно исключены (Radix/Base UI сами прокидывают такие в рантайме, их
никогда не будет в `tokens.css`).

### ⚠ Ловушка Figma Plugin API: `node.clone()` теряет `componentPropertyReferences`

Нашлась при добавлении `Indicator=right` в `Select / Item` и стоит отдельной заметки — не только
строкой в отчёте, потому что всплывёт у **любого** будущего клонирования варианта с вложенным
инстансом, чья видимость/контент управляется через привязку компонент-свойства (ровно так устроен
чек-марк Select, но так же может быть устроен любой будущий компонент со списком — Combobox,
Command, Context Menu в группе 4/5).

Механика: `родитель.children[i].componentPropertyReferences` — это способ, которым булево/текстовое
свойство компонента (`Selected#241:7` и т.п.) управляет свойством вложенного слоя (`visible`,
`characters`, `mainComponent`) без варианта на каждое сочетание. `node.clone()` копирует геометрию,
заливки, тексты, вложенность — **но не эту привязку**: у клонированного вложенного инстанса
`componentPropertyReferences` оказывается пустым объектом `{}`, хотя у оригинала там было
`{"visible": "Selected#241:7"}`. Внешне это выглядит как «чек-марк просто не появляется», а не как
ошибка — `setProperties({ Selected: true })` на инстансе отрабатывает без исключений, просто ничего
не происходит у клона (у оригинала — происходит).

Чинится явным переустановлением после клонирования: получить ссылку на тот же вложенный слой у
клона (имена сохраняются, поэтому `clone.findOne(n => n.name === '...')` работает) и присвоить
`node.componentPropertyReferences = { visible: 'Selected#241:7' }` заново, **до** любой проверки
через скриншот — присваивание само обновляет `.visible` до значения по умолчанию у определения
свойства (`false`), поэтому если слой изначально был скрыт на мастере (обычный способ построить
default-состояние для чек-марка/бейджа/индикатора), рестора `visible = true` отдельно не требуется.

Проверить, что привязка не потерялась — после любого клонирования с вложенными привязанными слоями
сравнить `componentPropertyReferences` клона с оригиналом (должны совпадать по ключам и значениям),
не полагаться на то, что скриншот «выглядит нормально» — у `Selected=false` по умолчанию разницы на
глаз всё равно не видно.

## Тот же чат — третий пункт: отступ/радиус панели Select относительно триггера

Третье отложенное расхождение проверил числами (Playwright: `getBoundingClientRect` +
`getComputedStyle`), не только скриншотом — результат разошёлся с тем, что было записано.

**Для size=md (единственный размер, который вообще моделирует Figma — у Select в Figma нет оси
Size) отступа и радиуса расхождения уже нет.** И в main, и в demo триггер и панель совпадают
точка-в-точку: радиус 8px/8px (main) и 4px/4px (demo) — оба элемента читают один и тот же
`VariableID:6:31` (`radius/lg`) и в Figma, и в коде (`rounded-lg` у обоих); отступ 4px что в Figma
(`content.y − trigger.bottom`), что в реальном рендере (`sideOffset` Radix). Похоже, это уже
починилось раньше как побочный эффект `f65d09d` (`position=popper` по умолчанию) и с тех пор не
перепроверялось числами — решение человека: закрыть пункт как решённый.

**Нашёлся новый баг, не из исходного списка: `SelectContent` игнорировал размер триггера.**
`SelectTrigger` при `size="sm"` красится в `rounded-md` (6px), но `SelectContent` был зашит на
статичный `rounded-lg` (8px) независимо от размера — при открытой панели у size=sm получался
видимый перепад радиуса между полем и панелью. Figma этот случай не моделирует вообще (нет оси
Size у Select), так что сравнивать было не с чем — нашли исключительно измерением кода.

Решение человека: радиус панели должен следовать размеру триггера, не быть зафиксирован. Технически
`SelectTrigger` и `SelectContent` — соседи под `<Select>`, а не родитель/потомок (`Content` уходит в
портал), поэтому размер напрямую не передать пропом. Сделано через контекст (`SelectSizeContext`,

Человек нашёл более богатую версию Avatar на ui.shadcn.com/docs/components/base/avatar (наш перенос
делался до того, как эти под-компоненты появились в реестре). Достал **реальный исходник** через
`WebFetch` на GitHub (`apps/v4/registry/new-york-v4/ui/avatar.tsx`), не по доке — у «base» в URL
доки не было отдельного registry/style, это просто категория в навигации, установка та же
(`shadcn add avatar`).

**Решено заранее (план/ответ человека), не додумывал по ходу:**
1. Ось `size`: у исходника теперь `default/sm/lg` = 24/32/40px — другие числа, чем наши `sm/md/lg` =
   32/40/48 (уже выпущенные, отревьюенные). Решение человека: **оставить нашу шкалу без изменений**
   (вариант A), ничего в геометрии/`figma-code-diff` уже сданного Avatar не трогать.
2. `AvatarBadge`: в исходнике `bg-green-600` — это код ТОЛЬКО примера использования в доке, не самого
   компонента (сам примитив — `bg-primary text-primary-foreground`, обобщённая точка). Решение:
   **без встроенного `status`-пропа** — дефолт `bg-primary`, паттерны online/busy/offline только в
   историях через `className` на инстансе (`bg-success`/`bg-danger`/`bg-surface-muted` — все три уже
   в каталоге с группы 1, новых токенов не заводил).

**Код** (`avatar.tsx`):
- `Avatar`: добавлен `data-size={size}` (дублирует `size` явным атрибутом) + `group/avatar` — по
  этому `AvatarBadge` читает размер родителя через `group-data-[size=…]/avatar:`, как в оригинале
  (сама геометрия `size-8/10/12` по-прежнему через `cva`, не через data-selector — наш обычный
  паттерн, не паттерн этого конкретного файла shadcn).
- `AvatarBadge`: `bg-primary text-on-primary ring-2 ring-surface`, размер `size-2.5/3/3.5` (10/12/
  14px) + иконка `size-2` (8px) на всех трёх ступенях — числа не придуманы: для sm/md у нас те же
  32/40px, что у shadcn `default/lg`, поэтому взял их badge-размеры 10/12 как есть; для нашего
  лишнего `lg`(48, у shadcn эквивалента нет) — продолжил их же арифметику +2 → 14px.
- `AvatarGroup`: `-space-x-2` (**−8px**, число из исходника, не придумано) + `*:data-[slot=avatar]:
  ring-2 ring-surface` (разделитель между перекрывающимися кругами).
- `AvatarGroupCount`: размер следует размеру аватаров в группе через `group-has-data-[size=…]/
  avatar-group:` (сами числа — 1:1 на наши три размера, а не уникальные, т.к. это просто «ещё один
  круг такого же диаметра»), `bg-surface-muted` + `typo-label-sm text-on-surface-muted`.

**Figma — два разных подхода по месту:**
- `AvatarBadge` — **не новые варианты набора Avatar**: его `root` — auto-layout, абсолютно
  позиционированный слой кольца сломал бы правило 7 `figma:layout` («в наборах компонентов нет
  абсолютных слоёв, кроме `focus-ring`» — расширять список исключений ради одной декоративной точки
  не стал, в отличие от `Slider` в своё время не было смысла перестраивать `Root` в плоский фрейм
  ради одной точки). Вместо этого — иллюстрация прямо в секции `Avatar`, под существующим набором:
  3 обычных (не auto-layout) обёртки с **экземплярами** `Avatar` (Size=sm/md/lg, Content=photo) +
  нарисованный кружок (`color/primary/default`, обводка `color/surface` 2px). Не компонент — секция
  не сканируется тем же правилом, что COMPONENT_SET.
- `AvatarGroup` — **отдельный компонент** (по прямой просьбе), новая секция после `Item`: auto-layout
  с `itemSpacing = −8` (raw, без переменной — это отрицание `spacing/2`, отдельного токена для
  отрицательных значений в системе нет и заводить не стал), 3 экземпляра `Avatar` (обводка `color/
  surface` 2px добавлена поверх инстансов) + нарисованный кружок-счётчик «+3» (`color/surface-muted`,
  `label/sm`, та же обводка). Свойство `Count` (TEXT) добавлено и привязано — то же решение, что у
  Badge/Kbd, не оставлять текст «голым» слоем.

**Две находки на сборке (сам, до отчёта):**
1. Опечатка в первой версии скрипта — координаты `badge-label`/`badge-row` внутри секции `Avatar`
   считал как `(узел.y − секция.y)`, будто `avatarSet.y` абсолютный; на деле координаты детей секции
   **уже относительные** (как и у Field/Input Group раньше) — дал гигантское отрицательное число,
   `resizeWithoutConstraints` упал валидацией `height ≥ 0`. Починил, весь скрипт безопасно
   переиграл (ничего не успело примениться — `use_figma` откатывает целиком при ошибке).
2. После добавления `AvatarGroup` `figma:layout` поймал два реальных новых случая правила
   «текстовый контейнер — Hug/Fill, не Fixed», которых не было видно раньше: (а) `count`-текст внутри
   нарисованного круга-счётчика (круг фиксированного размера по дизайну — тот же случай, что у
   Input/Textarea/Input OTP Slot, добавил exemption `"Avatar Group|avatar-group-count"`); (б) текст
   `initials` ВНУТРИ экземпляров `Avatar`, вложенных в `AvatarGroup`, — сам круг `Avatar` тоже
   фиксированного размера по дизайну, но это не ловилось раньше, потому что исходный скрипт сканирует
   на голый/fixed-текст только `variants[0]` каждого набора, а у Avatar это `Content=photo` (без
   текста вообще) — баг молчал, пока `Avatar Group` не вложил именно `Content=initials` варианты и не
   сделал их видимыми через рекурсивный обход инстансов. Добавил exemption `"Avatar|Avatar"` с
   пояснением в коде скрипта, почему он не всплывал раньше — не стал чинить саму сканирующую логику
   (глубже, чем нужно для этой задачи; существующее ограничение `variants[0]` работало для всех
   остальных 20+ компонентов).

### PR #3 — пилот + формат документации компонентов (в работе, эта ветка)

Задача: добавить в Storybook страницу документации на каждый компонент — назначение, когда
использовать, правила. Два языка (ru/en), переключение через глобальный тулбар.

**Утверждённый формат и правила (зафиксировать на будущее, применять ко всем компонентам):**

1. **Структура страницы — одна и та же для всех компонентов, 8 секций:** Назначение → Когда
   использовать → Когда не использовать (с чем заменить, если в наборе есть подходящий компонент)
   → Анатомия (реальные subcomponent'ы/слоты из кода) → Варианты и состояния (только то, что
   реально есть в коде/stories) → Правила контента → Доступность → Связанные компоненты. Плюс два
   необязательных поля вне этой нумерации: `variantGuidance` (правила выбора между вариантами,
   рендерится перед списком вариантов) и `forDevelopers` (технический раздел в конце страницы).
2. **Один источник контента на компонент** — `<component>.docs.ts` с типом `ComponentDocs`
   (`src/docs/types.ts`), поля `{ ru, en }` в одном месте, без дублирования в двух MDX. Рендер —
   через `src/docs/ComponentDocsPage.tsx` (один React-компонент на секцию, не монолит — чтобы в
   MDX можно было перемежать текст с `<Canvas of={...}/>` на реальные stories: живые примеры
   дополняют текст, не заменяют). Каждый `<component>.mdx` — тонкая обвязка: `<Meta of={...}/>`,
   `<Title/>`, секции `ComponentDocsPage` вперемешку с `<Canvas/>`.
3. **Язык** — `src/docs/locale.ts`, `useLocale()`. **Важное ограничение Storybook 10/addon-docs**:
   официальный хук `useGlobals()` из `storybook/preview-api` бросает "preview hooks can only be
   called inside decorators and story functions" и в свободном MDX-тексте, и внутри
   `<Story of={...}>` на Docs-странице (addon-docs компонует несколько сторей на одной странице,
   не оборачивает их в полноценный HooksContext — проверено руками). Рабочий способ — `DocsContext`
   (обычный React Context из `@storybook/addon-docs/blocks`): `storyById()`/`getStoryContext()`
   синхронно отдают актуальные globals. Требует, чтобы `<Meta of={...}/>` в MDX ссылался на
   реальный CSF-файл компонента — что и так нужно для `<Canvas/>`. Глобал `locale` в тулбаре
   (`.storybook/preview.tsx`), персистентность между страницами — штатный механизм Storybook (как
   у brand/theme), ничего дополнительного не потребовалось.
4. **Тон — для дизайнера/продакта, не для разработчика.** В Назначении/Когда использовать/Когда не
   использовать/Вариантах/Состояниях/Правилах контента — никаких Tailwind-классов, токенов,
   `data-slot`, Radix, npm-скриптов, CSS-поведения браузера. Всё это — в `forDevelopers`
   (рендерится последним, визуально приглушён: `typo-label-lg`/`body-sm` вместо
   `heading-3`/`body-md` у основных секций).
5. **Правила выбора — `variantGuidance`.** Не просто список вариантов с описанием, а иерархия и
   принципы: когда какой вариант брать, порядок элементов в группе, когда нужно подтверждение
   перед разрушительным действием. Для выбора МЕЖДУ компонентами (а не между вариантами одного) —
   в «Когда не использовать» с количественными ориентирами, если они общеотраслевые (например,
   2–5 вариантов выбора → радиокнопки, не выпадающий список) — но **только если компонент-замена
   реально есть в `src/components/ui`**, не предполагать.
6. **Ничего не выдумывать.** Варианты/состояния — только то, что есть в `cva()` и stories.
   Правила выбора — только общеотраслевые (как в Material/Carbon/Atlassian), не предположения о
   нашем продукте. Если неочевидно (например, порядок кнопок в диалогах — какая сторона у

7. **Правила контента** — только про текст (формулировки, длина, регистр, порядок опций,

8. Русский текст — «скринридер» (не «screen reader'у»); EN — нормальный технический английский, не
