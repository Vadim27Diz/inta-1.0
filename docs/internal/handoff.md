## Решение (общее для всех компонентов с INSTANCE_SWAP на иконке)

Вариант «б»: слот-иконка — **прямой инстанс `Icon base` (`115:5`, id `115:5`) с
`isExposedInstance=true`**, а не плоское свойство на корне (это физически невозможно — Figma не
выводит `INSTANCE_SWAP` на корень без промежуточного инстанса). В панели Properties это даёт
отдельную секцию по имени слоя с полем «Glyph». Общие `Icon` (`115:32`) и `Icon base` не трогаем.

### Проверки поведения (на одноразовых тестовых инстансах, удалены после теста) — пройдены для всех 4

- Заливка следует за токеном после смены глифа (не замораживается) — проверено сменой глифа на
  произвольный (`li:star`) и обратно.
- Глиф и заливка переживают переключение структурной оси варианта (`Size` у Avatar, `Variant`/`Size`
  у Item, `Media` у Empty, `Variant` у Alert).
- **Alert отдельно:** подтверждено оба сценария — (1) инстанс БЕЗ ручного оверрайда глифа при смене
  `Variant` корректно получает глиф+заливку именно новой ветки (`default→info→success→warning→
  danger`, каждый раз верная пара); (2) инстанс, где глиф явно переопределён вручную (через
  `setProperties` — то же самое, что выбор в поле «Glyph»), сохраняет этот ручной выбор при смене
  `Variant` (override «побеждает» дефолт новой ветки) — тот же механизм, что и у Button при
  переключении `Size`, ожидаемо и корректно.

## Решения человека по остальным компонентам с иконками

- **Select (триггер): миграция НЕ нужна.** Шеврон (closed/open/focus) — зашитый глиф по дизайну,
  присоединяется к списку исключений для будущего правила `figma:layout`, та же категория, что
  Checkbox `mark`, чекмарк `Select / Item`, шеврон `Native Select`. Не трогать.

## Card (`media`) — только чтение, отчёт

`media` — пустой `FRAME` (`children: []`) в самом мастер-компоненте, `Media#410:3` — обычный
boolean. **Иконки там нет ни в одной схеме использования** — ни в мастер-компоненте, ни в известных
инстансах. Похоже на плейсхолдер под фото (image fill добавляется per-instance), не часть системы
Icon/Icon base. Рекомендация: не включать Card в трек миграции иконок, пока не найдётся реальный
инстанс, где `media` фактически используется под иконку. Правок не вносилось.

## План: Toggle (только план, миграция не начата)

**Почему это не «ещё один Avatar».** У остальных 10 компонентов файла слот-иконка — инстанс `Icon`
(или `Icon/Size=N`), который сам оборачивает `Icon base`. У Toggle `icon` — **прямой инстанс
`li:star`**, без `Icon`/`Icon base` в цепочке вообще (подтверждено на всех 3 размерах и всех 18
инстансах `Toggle Group` + 16 на `Playground` — 100% `li:star`, 0 оверрайдов). `li:star` сам по себе
не имеет `INSTANCE_SWAP`-свойства — оно есть только на `Icon base`. Значит путь не «проставить
`isExposedInstance=true` на существующем слое» (как у остальных), а **заменить мастер-компонент
слота** с `li:star` на `Icon base` — операция другого типа: не expose, а component swap, с переносом
размера/заливки на новый инстанс тем же способом, что у остальных (`setBoundVariableForPaint`).

**Масштаб:** 36 вариантов самого набора + 18 инстансов `Toggle Group` (эти не независимы — имя слоя
совпадает, но при смене мастер-компонента у самого набора нужно отдельно проверить, не рвёт ли это
даунстрим как в баге delete+recreate из Button, см. `handoff-archive.md` или сам PR #9) + 16 на
`Playground`. Итого потенциально тронутая поверхность — на порядок больше, чем у любого компонента
этого пакета.

**Риски:**
1. Замена мастер-компонента инстанса (а не просто `createInstance`+`isExposedInstance`) — API-путь
   не опробован в этом файле, нужно явно проверить, что `swapComponent`/эквивалент не роняет текущие
   95%+ default-оверрайдов так же, как рисковало delete+recreate.
2. 34 даунстрим-инстанса (Toggle Group + Playground) — все сейчас на дефолтном `li:star` без
   оверрайдов (это хорошая новость: восстанавливать нечего), но после замены мастер-компонента нужно
   сверить, что ни один не осиротел.
3. Токен заливки `icon` слоя у Toggle не проверялся в рамках этого плана (отдельный шаг перед
   миграцией — как у Button/Avatar/Item/Empty/Alert, нужен быстрый read перед тем как трогать).
4. Больше поверхность = больше времени на сверку «до/после» — пакетами по оси (например по
   `Size`), не всё сразу.

## Пробелы (общие, накопленные)

- **`scripts/figma-code-diff.mjs` не проверяет Button вообще** (и остальные компоненты этого пакета
  тоже не проверялись — не было такой секции изначально). Отдельная задача.
- **`figma/layout.json` не пересняты.** Попытка пересъёма 2026-10-22 вскрыла, что страница
  `Components` в Figma уже перестроена в многоколоночную сетку (секции на x = -2236…6830, несколько
  колонок вместо одной) и расходится с текущим снимком на 31 пункт (порядок секций, «не одна
  колонка», зазоры) — **pre-existing дрейф, не вызванный ни одной из задач этой сессии**. По решению
  человека снимок не пересохранён; `npm run verify` зелёный, потому что `figma:layout` сверяет
  сохранённый снимок сам с собой, а не с живой Figma. **Нужно решение человека** про грид vs одна
  колонка, прежде чем переснимать.
- **Правило `figma:layout` для «слот-иконка без экспонированного Glyph»** — план есть (ниже), в код
  не добавлялось по явной просьбе (только чтение).
- **Когда будем переснимать `figma/layout.json`/делать правило:** экспортёр
  (`figma-layout-export.js`) должен читать скрытые слоты с `figma.skipInvisibleInstanceChildren =
  false` (уже делали так во всех read-скриптах этой сессии) и сканировать **не только
  `variants[0]`, а минимум по одному варианту на значение структурной оси** (например `Size`) — не
  только первый вариант сета. Уточнение появилось при планировании текущего пакета: разные размеры
  одного компонента иногда имеют разную структуру слота (напр. у Avatar `Icon/Size=16|20|24` — имя
  инстанса меняется с размером), и сканирование только `variants[0]` эту разницу не ловит.

## План: правило `figma:layout` для экспонированного Glyph (только план, не в коде)

**Снимок сегодня:** не содержит данных об `isExposedInstance`/`mainComponent` слота ни в одном
массиве (`sections`, `components`, `absoluteLayers`, `ringClipping`, `textContainers`, `nakedText`,
`listItemSizing`, `repeatedLayers`, `focusRingShape`).

**Что ловить:** для каждого топ-level компонента — слои с именами `icon`, `icon-left`, `icon-right`,
`leading-icon`, `trailing-icon`, `media`, `indicator`, `mark`; флагать, если слой НЕ прямой
экспонированный инстанс `Icon base` с доступным `Glyph`.

**Исключения (зашитые глифы, не баг):** Checkbox `mark`, чекмарк `Select / Item`, шеврон `Select`
(добавлено решением выше) и `Native Select`.

**Снимок нужно расширить:** новый массив `iconSlots: [owner, layer, isExposedInstance,
hasReachableGlyphSwap, exemptReason|null]`, собирать **не только по `variants[0]`, а минимум по
одному варианту на значение каждой структурной variant-оси** (см. «Пробелы» выше — это уточнение
обязательно для корректности правила, не только для раскладки).

**Закрытие пробела по Button/остальным в `figma:diff`:** это ДРУГОЙ скрипт
(`scripts/figma-code-diff.mjs`, параллель/геометрия computed-style vs код) — новое правило
`figma:layout` его не закрывает. Нужна отдельная секция в `figma-code-diff.mjs` на каждый
мигрированный компонент, отдельная задача.

## Правила

- Figma: чужие объекты не удалять/не переписывать без вопроса (не нарушалось во всём пакете).

- Один компонент — одна миграция со своей сверкой «до/после»; один пакет компонентов — один PR.
