## Аудит Button — результат (read-only, 2026-10-24)

**Структура набора не пострадала.** `componentPropertyDefinitions` набора `Button`
(id `87:298`, fileKey `uUb84csG4wOfbUjB38ODiz`, страница `Components`):
- `Type` (VARIANT, новое свойство человека): `Button` | `Icon Button`, default `Button`.
- `Variant` (VARIANT, не менялось): 10 значений, primary…link-danger.
- `Size` (VARIANT, не менялось): sm, md, lg, icon, icon-sm, icon-lg.
- `State` (VARIANT, не менялось): default, hover, pressed, focus, disabled.
- `Label`/`Icon left`/`Icon right` — те же BOOLEAN/TEXT свойства, не менялись.

Число вариантов **не изменилось: 300** (10×6×5, как в прежнем снимке). `Type` не умножил комбинации —
он лёг поверх уже существующего деления `Size`: `Type=Button` встречается только с `Size∈{sm,md,lg}`,
`Type=Icon Button` — только с `Size∈{icon,icon-sm,icon-lg}`, без исключений, во всех 10×5 сочетаниях
`Variant×State` для каждой группы. Переименований/пропавших значений `Variant`/`Size`/`State` нет —
единственное видимое последствие редактирования: имя каждого варианта теперь начинается с
`"Type=Button, "` или `"Type=Icon Button, "` (было без этого префикса).

**Паддинги/радиус — согласия 50/50 внутри каждой из 6 групп `Type×Size`, все на токенах
`spacing/*`/`radius/md`, без расхождений.** Группы и их паддинги (все — алиасы на переменные,
не хардкод):

| Type × Size | pL/pR | pT/pB | gap | w (мод) | h | радиус | переменные |
|---|---|---|---|---|---|---|---|
| Button / sm | 12 | 0 | 8 | 63 | 32 | 6 | spacing/3, spacing/0, spacing/2, radius/md |
| Button / md | 16 | 8 | 8 | 77 | 36 | 6 | spacing/4, spacing/2, spacing/2, radius/md |
| Button / lg | 24 | 0 | 8 | 99 | 40 | 6 | spacing/6, spacing/0, spacing/2, radius/md |
| Icon Button / icon-sm | 0 | 0 | 8 | 32 | 32 | 6 | spacing/0 везде |
| Icon Button / icon | 0 | 0 | 8 | 36 | 36 | 6 | spacing/0 везде |
| Icon Button / icon-lg | 0 | 0 | 8 | 40 | 40 | 6 | spacing/0 везде |

Это **совпадает с `button.tsx`** (cva `size`: sm → h-8/px-3, md → h-9/px-4/py-2, lg → h-10/px-6,
icon* → size-9/8/10) один в один. Высота (`h`) — 50/50 без единого выброса в ЛЮБОЙ из 6 групп.

**Единственный реальный выброс — ширина `+2px` у всех 15 инстансов `Variant=outline` (Button,
все 3 размера × 5 состояний).** Это не «паддинг 0 у кого-то» (паддинги у outline идентичны остальным
вариантам того же размера — проверено точным сравнением `86:44` outline-lg-default против `85:44`
primary-lg-default: `pL=pR=24` у обоих, `label` тот же текст `"Button"` той же ширины 51, иконки
скрыты у обоих). Причина — свойство узла **`strokesIncludedInLayout: true`** у outline-варианта:
Figma включает толщину обводки (`strokeWeight: 1`, `strokeAlign: "INSIDE"`) в расчёт hug-ширины
auto-layout фрейма, добавляя `+1px` на сторону, хотя CSS `border` в коде (`border-box` по умолчанию
в Tailwind preflight) этого не делает — рамка рисуется внутри уже заданной ширины, не раздувая её.
**Это не последствие правки `Type`** — свойство `strokesIncludedInLayout` стоит на самом компоненте
independent от `Type`/`Size`, скорее всего было так и до сегодняшней правки, просто никогда не
попадало под проверку: `figma-code-diff.mjs` для `outline` сверяет только `border`-токен/цвет, не
ширину (строки 82–91 скрипта), поэтому `npm run figma:diff` этого не увидит ни сейчас, ни раньше.
Не относится к иконочным кнопкам — там `primaryAxisSizingMode`/`counterAxisSizingMode` обе `FIXED`
(жёсткий квадрат), stroke не участвует в размере независимо от `strokesIncludedInLayout`.

**Инстансы Button в файле — все согласованы, ничего не сломалось.** Проверено 136 инстансов на всех
4 страницах файла (`Components`: 11, `Playground`: 100, `Page 4`: 25, `Foundations`: 0) —
у каждого `componentProperties.Type` совпадает с ожидаемой парой для его `Size` (`Button`↔sm/md/lg,
`Icon Button`↔icon/icon-sm/icon-lg), ни одного рассинхрона. В частности инстанс `action` в `header`
карточки (Card action, id `410:451`) — корректно `Type=Icon Button, Variant=ghost, Size=icon`.

**Что реально затронуто правкой `Type` (не критично, но учесть при следующем пересборе снимка):**
имя каждого варианта Button в живой Figma теперь несёт префикс `"Type=…, "`. Committed
`figma/layout.json` → массив `iconSlots` хранит старые имена вариантов Button БЕЗ этого префикса
(например `"Variant=primary, Size=lg, State=default"` вместо текущего
`"Type=Button, Variant=primary, Size=lg, State=default"`). Экспортёр
(`.claude/skills/design-tokens/assets/figma-layout-export.js:386`) пишет `variant.name` как есть, так
что при следующей живой пересъёмке снимка эти строки изменятся — сейчас `npm run figma:layout` этого
не замечает (скрипт не ходит в Figma, сверяет только самосогласованность сохранённого файла и хеш
экспортёра), это тот самый документированный в SKILL.md класс дыр («снимок и реальная Figma
расходятся молча», раздел Definition of Done п.9). Не чинил, только зафиксировал.

незадокументированная страница **`Page 4`** (id `233:851`, верхнеуровневые дети: `Main / Light`,

## Открытые решения — доступность (roadmap.md п.4)

Ждут ответа человека, варианты сохранены дословно из отчёта в чате:

1. **Badge `focus-visible`** — решения не нужно, механическая правка: добавить в `badgeVariants`
   паттерн `focus-visible:outline-solid focus-visible:outline-2 outline-offset-2 outline-focus-ring`
   (как у Item/BreadcrumbLink/Slider-thumb), токен `outline-focus-ring` уже существует. Поправить
   `badge.docs.ts:96-97,111-112` — убрать «добавляйте кольцо сами». Фигма не трогается: у Badge
   component set нет свойства `State`, значит и нет визуального состояния focus для проверки.
2. **Skeleton `aria-busy`/`role`** — решение не принято. Проблема с автопропом: Skeleton обычно
   используют группой (несколько плейсхолдеров в одном разделе загрузки); `role="status"` на КАЖДОМ
   элементе группы озвучит статус скринридеру несколько раз подряд. Варианты на выбор человека:
   а) оставить как сейчас (только документация, без кода); б) необязательный проп, который рендерит
   `aria-busy`/`role="status"` сам — риск: не решает проблему множественного объявления в группе без
   доп. правил; в) другой API — не предложен, нужно обсуждать отдельно.
3. **Разнобой языка sr-only/aria-label** — решение не принято. Факты: `Spinner`→"Загрузка" (RU),
   `Breadcrumb`→`aria-label="breadcrumb"` (EN, по WAI-ARIA Authoring Practices это буквальная
   рекомендация), `BreadcrumbEllipsis`→sr-only "More" (EN). В проекте нет i18n-механизма для строк
   компонентов. Нужен выбор языка (RU везде / EN везде / проп для локали) — зависит от решения
   человека, не предлагал сам вариант как дефолт.
4. **Field `aria-describedby`** — решение не принято. Field — «рыхлая» композиция
   (`field.stories.tsx:25-33`): не владеет контролом-ребёнком и не знает id `FieldDescription`/
   `FieldError`, чтобы прокинуть автоматически. Автосвязка возможна только через смену архитектуры
   (контекст + `useId`, или клонирование детей по `data-slot`) — ломает текущую гибкость API.
   Нужен выбор подхода до реализации.
5. **Slider `aria-labelledby`** — решение не принято. Сейчас только `thumbLabel` (строка/массив) →
   `aria-label` на `Thumb` по индексу (`slider.tsx:11-16,58`). `aria-labelledby` не принимается вовсе
   (проп уходит в `{...props}` на `Root`, не на `Thumb`). Нужно решить: принимать оба способа
   (`thumbLabel` и новый `thumbLabelledBy`) одновременно или заменить один другим — до реализации.

**Ручная проверка за человеком (не автоматизируется):** Item `asChild` внутри `ItemGroup` —
обёртка `role="listitem"` с `display:contents` (`item.tsx:84-89`). Playwright подтверждает роль и
`display:contents` в Chromium; нужна проверка в реальном Safari + VoiceOver (⌘F5), навигация до
такого пункта, должен объявляться «list item N of M». Если роль не долетает — заменить обёртку на
аналог без `display:contents`.
