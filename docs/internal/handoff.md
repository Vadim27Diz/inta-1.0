# Handoff: Figma Button — icon-left/icon-right как INSTANCE_SWAP

Текущее состояние на 2026-10-22. История предыдущих задач (документация компонентов, Storybook UI
Этап 1) — `handoff-archive.md`. **Правило:** этот файл перезаписывается при каждом обновлении, не
дописывается в конец.

## Статус: PR открыт, не смёржен

[PR #9](https://github.com/Vadim27Diz/inta-1.0/pull/9), ветка `feat/button-icon-glyph`.

## Решение

Вариант «б» из обсуждения до переполнения контекста: слоты `icon-left`/`icon-right` в Button —
**прямые инстансы `Icon base` (`115:5`) с `isExposedInstance=true`**, а не плоское свойство
«Icon left» на корне (это физически невозможно — Figma не выводит `INSTANCE_SWAP` на корень без
промежуточного инстанса). В панели Properties это даёт отдельную секцию по имени слоя
(`icon-left` / `icon-right`) с полем «Glyph». Общие `Icon` (`115:32`) и `Icon base` не трогали.

## Что сделано

- Мигрированы все 200 вариантов Button (`87:298`, пакетами: пилот 1 → md+sm 99 → lg 50 → Size=icon
  50). Заливка каждого слота явно перепривязана к исходному токену варианта.
- Код (`src/components/ui/button.tsx`): `[&_svg]:size-4` перенесён с базового класса в
  `sm`/`md`/`icon`, `lg` получил `[&_svg]:size-5` — иконка 16→20px, единственное визуальное отличие.
- Аудит иконок по всем 11 компонентам файла с собственным слоем-иконкой — `figma-icon-audit.md`.
  Instance swap на корне есть теперь только у Button; у остальных 10 — не трогали (вне рамок).

## Баги миграции и их механизм (пригодится для следующих компонентов)

1. **Delete+recreate слота рвёт оверрайды даунстрим-инстансов.** Figma хранит оверрайд инстанса по
   внутреннему id узла внутри мастер-компонента; если слот удалить и создать заново (а не
   мутировать на месте), у нового узла новый id — старые оверрайды сиротеют и откатываются к
   дефолту. Так потерялся `li:settings` вместо дефолтного `li:plus` на `action` в Card
   (`410:451`, единственный реальный оверрайд во всём файле). Восстановлен точечно через
   `setProperties`. **Вывод:** инвентаризация даунстрим-инстансов обязательна и ДО, и ПОСЛЕ.
2. **`createInstance()` + `INSTANCE_SWAP` не наследует заливку слота.** Новый вложенный инстанс
   глифа подхватывает свой собственный дефолтный fill-токен мастер-компонента, а не токен, что был
   у заменяемого слота. Чинится явной привязкой `figma.variables.setBoundVariableForPaint` сразу в
   скрипте миграции, по снимку «до».
3. **Смена глифа через drill-in может заморозить заливку как персональный оверрайд инстанса**,
   если в момент смены заливка слота ещё не была исправлена багом 2 — сам факт тестовой проверки
   создаёт новый оверрайд, который потом тоже нужно сверять со снимком.
4. **Скрытые слоты (`visible=false`) отдают пустой `.children` через Plugin API по умолчанию** —
   читать с `figma.skipInvisibleInstanceChildren = false`, иначе проверка «до» не увидит то, что
   реально есть внутри.

## Чек-лист миграции компонента (используй для Select-триггера, Toggle, Item, Empty, Card, Alert)

1. **Инвентаризация оверрайдов ДО** — найти все инстансы компонента вне самого набора (другие
   секции `Components`, `Playground`, `Foundations`) и сохранить их текущее состояние глифа/
   заливки/видимости в JSON-снимок (`figma.skipInvisibleInstanceChildren = false`).
2. **Снимок «до» самого набора** — глиф/заливка/видимость/размер каждого варианта, с ключом для
   сверки (см. `figma-button-icons-before.json`).
3. Миграция слота — мутировать на месте там, где возможно; если delete+recreate неизбежен,
   отдельным шагом перенести даунстрим-оверрайды из снимка (1) через `setProperties`/
   `setBoundVariableForPaint`, не полагаясь на то, что Figma сделает это сама.
4. **Сверка ПОСЛЕ** — снимок (2) против текущего состояния, 0 расхождений кроме заранее одобренных;
   снимок (1) против текущего состояния даунстрим-инстансов, 0 потерянных оверрайдов.
5. Проверка поведения: цвет следует за `Variant`/`State` после смены глифа; глиф/заливка/размер
   переживают переключение размеров варианта (`md ↔ lg` и т.п.) — на одноразовом тестовом
   инстансе, который потом удалить.
6. Код + `npm run verify` + `tsc -b` + `npm run build-storybook`.
7. Что осталось открытым — см. «Пробелы» ниже, не придумывать покрытие постфактум.

## Пробелы (не закрыты этим PR)

- **`scripts/figma-code-diff.mjs` не проверяет Button вообще** — нет ни одной секции `Button`/
  `button`. План закрытия — читать план ниже (`roadmap.md` → пункт по Button) или отдельный чат.
- **`figma/layout.json` не пересняты.** Definition of done требует пересъёма перед мёржем (пункт
  9) — попытка пересъёма 2026-10-22 вскрыла, что страница `Components` в Figma уже перестроена в
  многоколоночную сетку (секции на x = -2236 … 6830, несколько колонок вместо одной) и расходится
  с текущим снимком на 31 пункт (порядок секций, «не одна колонка», зазоры). Это **pre-existing
  дрейф, не вызванный этой задачей** — Button как был, так и остался на x=-64, без изменений
  геометрии. По решению человека снимок не пересохранён, `npm run verify` в PR зелёный, потому что
  `figma:layout` сверяет сохранённый снимок сам с собой, а не с живой Figma. **Нужно отдельное
  решение человека**: кто/когда переставил секции в грид, осознанная ли это перестройка (тогда
  обновлять `ORDER`/правило «одна колонка» в `scripts/figma-layout-check.mjs` и
  `figma-layout-export.js` под новую раскладку) или нет (тогда возвращать Figma к одной колонке).
  Делать это нужно до следующего `npm run figma:layout` пересъёма любого компонента — иначе
  каждая следующая задача будет натыкаться на те же 31 нарушение.
- **Chromatic** покажет изменения `lg`-кнопок с иконками (16→20px) — ожидаемо, не регрессия.

## Правила

- Figma: чужие объекты не удалять/не переписывать без вопроса (не нарушалось — Icon/Icon base не
  трогали).
- Новый глобальный токен — не потребовался в этой задаче.
- Каждый шаг миграции — отдельный пакет вариантов, см. «Что сделано».
