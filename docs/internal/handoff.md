## Ловушка сессии: `Write` вместо `Edit` стёр архив

При первой попытке дописать новую запись в `docs/internal/handoff-archive.md` использовал `Write` —
этот инструмент **перезаписывает файл целиком**, а не дополняет. Результат: из 1723 строк архива
осталось 36 (потеряно 1710 строк истории). Сразу восстановлено `git checkout -- docs/internal/handoff-archive.md`
(репозиторий был чист на тот момент, откат безопасен), затем запись вставлена правильно — через
`Edit` с заменой первой строки на новый блок + старое содержимое ниже.

**Механизм:** `Write` не читает-и-дополняет, он задаёт новое содержимое файла целиком, независимо от
того, что там было. Любой файл, который по правилу «дописывается в начало, не перезатирается»
(архивы, логи, CHANGELOG-подобные файлы) — трогать только `Edit` (заменяя первую строку/маркер на
`новый_блок + старое_содержимое`), никогда `Write`, даже если перед этим файл был прочитан целиком.
**Перед такой правкой — `git status`, чтобы откат через `git checkout --` был возможен**, если
ошибка всё же повторится.

## Аудит Button — уточнение после решений человека (2026-10-24)

Человек принял: структура (300 вариантов, `Type` не умножил комбинации), паддинги/радиус на

### 1. `strokesIncludedInLayout` — уточнение масштаба (было «15», на самом деле 30)

Человек решил: выключить `false` только у вариантов с видимым `+2px`-багом. При подготовке
структурной проверки (см. ниже) выяснилось, что **флаг `strokesIncludedInLayout=true` стоит на ВСЕХ
300 вариантах Button** (проверено явно: `85:44` primary — `true`, `86:139` ghost icon — `true`), не
только на outline. Он безвреден там, где нет самой обводки (`strokes.length === 0`) — именно поэтому
видимый баг был только у `Variant=outline`.

Но и у outline его **30 вариантов с реальной обводкой**, не 15:
- **15 в `Type=Button`** (lg/md/sm × 5 states, Hug-ширина) — здесь баг **видимый**: `+2px`
  (101/79/65 вместо 99/77/63).
- **15 в `Type=Icon Button`** (icon-lg/icon/icon-sm × 5 states, Fixed-размер) — здесь баг
  **латентный**: та же неверная настройка, но `primaryAxisSizingMode`/`counterAxisSizingMode` обе
  `FIXED` у Icon Button, поэтому `strokesIncludedInLayout` сейчас ни на что не влияет визуально.

**Открытое решение (новое, не было в прошлой записи):** чинить только 15 видимых (минимум,
достаточно для бага) или все 30 (устойчивее — если когда-нибудь Icon Button/outline поменяют на Hug,
баг не вернётся молча). Рекомендация: все 30 — именно это сочетание (видимая обводка +
`strokesIncludedInLayout=true`) нигде не нужно по правилу «обводка не меняет размер», независимо от
текущего sizing mode. Жду ответа.

### 2. Паддинги — план значений (без паддинга 0), код не трогать

Посчитано по контенту: `line-height` текста (`typo-label-sm`=16, `-md`=20, `-lg`=24, из
`token-catalog.md:136-146`) и иконка (16px у sm/md, 20px у lg — из `button.tsx` `[&_svg]:size-4`/`size-5`).
Вертикальный паддинг = `(Fixed-высота − max(line-height, иконка)) / 2`. Для Icon Button — паддинг
со всех 4 сторон = `(квадрат − иконка) / 2`.

| Type × Size | контент | сейчас (pad) | → предложено | токен | проверка (контент+2×pad = высота/квадрат) |
|---|---|---|---|---|---|
| Button / sm | 16 (line-height=icon) | pT/pB **0** | **8** | `spacing/2` | 16+16=32 ✓ |
| Button / md | 20 (line-height) | pT/pB 8 (не трогать) | 8 | `spacing/2` (уже) | 20+16=36 ✓ |
| Button / lg | 24 (line-height) | pT/pB **0** | **8** | `spacing/2` | 24+16=40 ✓ |
| Icon Button / icon-sm | 16 (иконка) | все стороны **0** | **8** | `spacing/2` | 16+16=32 ✓ |
| Icon Button / icon | 16 (иконка) | все стороны **0** | **10** | `spacing/2-5` | 16+20=36 ✓ |
| Icon Button / icon-lg | 20 (иконка) | все стороны **0** | **10** | `spacing/2-5` | 20+20=40 ✓ |

Оба токена — `spacing/2` (8px) и `spacing/2-5` (10px) — **уже существуют** в коллекции `Primitives`
(проверено живым чтением: `spacing/0` … `spacing/96`, включая все `N-5` половинные шаги). Ничего
придумывать не пришлось, новый токен не нужен.

**Код (`button.tsx`) трогать не нужно.** Все 6 проверок выше — точное равенство (контент + 2×паддинг
= высота/квадрат), поэтому в браузере результат пикселько идентичен и до, и после: сейчас
центрирование достигается через Fixed-высоту/квадрат + `items-center` без явного паддинга в CSS,
после правки — то же самое визуально, просто у Figma-рамки будет явный ненулевой паддинг вместо
пустого места. **Chromatic-диффа не будет** — это не предположение, это следствие точного равенства
в таблице выше. Код не менял, ждёт отдельного ОК, если человек всё же захочет синхронизировать
`py-2`/`p-2`/`p-2.5` в код для буквального соответствия модели (необязательно).

### 3. Проверка в скриптах — добавлено и проверено живыми данными, снимок НЕ пересобирался
