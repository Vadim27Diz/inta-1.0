## Принятые решения (эта сессия)

1. **Правило порядка Size** — для ЛЮБОГО свойства, названного `Size`, включая числовые (Icon:
   `12,16,20,24,32,40` → должно стать по убыванию), порядок всегда от большего к меньшему.
   **Исключение: `Utility / Focus ring` → `Scale`** — другое имя свойства (не `Size`), правило на
   него не распространяется. **Не сделано:** это исключение нужно записать в
   `.claude/skills/figma-component-conventions/SKILL.md` — решение принято, текст в скилл ещё не
   внесён (отвлёкся на часть А). Первый шаг следующей сессии.
2. **Item не трогаем** — его `Size: ["default","sm"]` совпадает с кодом (`item.tsx`), это не
   нарушение, а другая, уже согласованная конвенция для этого компонента.
3. **Способ перестановки порядка — ручной, человеком, в Figma UI** (drag в списке значений
   variant-свойства). **Клонирование агентом отвергнуто** — риск: удаление/пересоздание варианта при
   реордеринге ломает существующие инстансы (ссылки на конкретный вариант по компоненту, не по
   имени). Я сверяю `figma:layout`/`figma:diff` после того, как человек переставит.
   - Набора, которые нужно переставить (порядок сейчас → должен стать): Input `md,sm,lg`→`lg,md,sm`;
     Native Select `sm,md,lg`→`lg,md,sm`; Toggle `sm,md,lg`→`lg,md,sm`; Toggle Group
     `sm,md,lg`→`lg,md,sm`; Avatar `sm,md,lg`→`lg,md,sm`; Icon `12,16,20,24,32,40`→`40,32,24,20,16,12`.
   - Механика, установленная тестом на одноразовом наборе (создан и полностью удалён в прошлой
     сессии): порядок `variantOptions` фиксируется в момент создания узла-значения, не меняется от
     порядка слоёв/дерева/`combineAsVariants`, не меняется переименованием. Плагин-API не даёт прямого
     метода перестановки (`editComponentProperty` не поддерживает `variantOptions`). Поэтому
     перестановка — только руками в UI.
4. **Label/Field — вариант A**, область **только Input**:
   - `size` у Label — свой проп (cva), не наследуется автоматически ни от чего.
   - `size` у Field — прокидывается в `FieldLabel` через контекст; **в Input не прокидывается** —
     разработчик ставит тот же `size` на Input вручную. Задокументировано в `field.docs.ts`.
   - Textarea (своего `size` нет вовсе) и Select (в Figma нет свойства `Size`, в коде своя шкала
     высот sm/md на 7/8px против 8/9/10px у Input/Native Select — **расхождение внутри системы**) —
     НЕ в объёме этой задачи, записаны в `field.docs.ts` → `openQuestions` как будущие отдельные
     задачи (см. бэклог ниже).
5. **Типографика Label — предварительно**: `sm→typo-label-sm` (12/16), `md→typo-label-md` (14/20,
   без изменений), `lg→typo-label-lg` (16/24, токен уже существовал, уже использовался в
   `FieldLegend` variant=legend). **Финально — после скриншота** (см. часть В ниже) — человек может
   попросить альтернативу, если подпись при `sm` будет выглядеть странно рядом с полем.

## Часть Б — что делать, когда человек даст «версия сохранена» (не начато)

Порядок из задания человека, без отклонений:
1. Label: добавить `Size` = `lg, md, sm` — **создавать значения сразу в этом порядке** (порядок
   фиксируется при создании, см. решение 3 выше — ошибиться здесь нельзя исправить перестановкой
   без того же риска для инстансов).
2. Field: добавить `Size` = `lg, md, sm`, тоже создавать в этом порядке. В каждом варианте — зашитый
   инстанс Label того же Size и Input того же Size (без новых INSTANCE_SWAP-свойств — просто прямая
   привязка варианта, как сейчас zашито на `Size=md, State=default`).
3. **Перед любой записью** — тест на одноразовом наборе (не из документации, живым чтением):
   `ComponentSetNode.defaultVariant` и какое значение `Size` получает НОВЫЙ инстанс при вставке —
   нужно узнать, действительно ли дефолт = `variantOptions[0]` (как было с `defaultValue` в прошлом
   тесте на `TEST_ORDER_1`) и как это соотносится с `defaultVariant`. Создать/проверить/**удалить**
   тестовый набор, как в прошлый раз.
4. Дефолт набора — `md`, не первое значение `lg`. Если `defaultVariant`/`variantOptions[0]`
   действительно определяют дефолт автоматически на `lg` — после создания свойства явно проставить
   дефолт на `md` (или на всех мигрируемых инстансах явно выставить `Size=md`, см. п.5).
5. **Миграция 10 существующих инстансов** (все на странице Playground, не в Components):
   - `Label` отдельно: id `310:870` (Main/Light), `310:1201` (Main/Dark), `310:1515` (Demo/Light),
     `310:1829` (Demo/Dark) — путь `… > surface-raised(FRAME) > Frame(FRAME) > Label(INSTANCE)`.
   - `Field`: id `310:923`, `310:931` (Main/Light), `310:1254`, `310:1262` (Main/Dark), `310:1568`,
     `310:1576` (Demo/Light), `310:1882`, `310:1890` (Demo/Dark) — путь `… > Forms(FRAME) >
     Frame(FRAME) > Field(INSTANCE)`. Каждый несёт вложенный `Label`-инстанс того же пути
     (`I<fieldId>;207:193` или `;207:200`).
   - После того как у набора появится `Size`, проверить: эти 10 инстансов должны остаться
     `Size=md` (не съехать на новый дефолт/первое значение). Если съехали — проставить `Size=md`
     явно на каждом.
6. Снимок «до» (как для Button — `docs/internal/figma-label-field-size-before.json` по аналогии),
   пилот на одной паре (например Field `Size=lg, State=default`), сверка, затем пакеты, сверка после
   каждого.
7. Правило в `figma:layout`/`figma-layout-export.js`: одинаковый набор и порядок значений `Size` у
   Label, Field и Input (чтобы будущий рассинхрон ловился автоматически, не только для Button —
   обобщить логику `sizeConsistency`).
8. Пересборка `figma/layout.json`, `npm run verify`, `tsc -b`.
