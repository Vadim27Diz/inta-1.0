# Аудит иконок в компонентах Figma (Inta 1.0) — свойства на корне

Дата: 2026-10-21 (обновлено, заменяет первую версию отчёта).
Файл: `Inta 1.0`, fileKey `uUb84csG4wOfbUjB38ODiz`, страница `Components` (`38:2`).

## Что изменилось по сравнению с первой версией

Первый прогон (через `get_metadata`, только XML-метаданные) проверял лишь «instance
или нарисованный слой» и из-за этого **дал ложный результат по `Select / Item` →
`indicator`**: инструмент показал пустой `<frame>` без детей, хотя на деле внутри
есть скрытый `instance` иконки — `get_metadata` обрезает глубоко вложенные скрытые
слои и не показывает их. Этот отчёт — пересчёт тем же вопросом, который на самом
деле нужен: **выведена ли иконка свойством на корне компонента**, через Plugin API
(`componentPropertyDefinitions` корня + `componentPropertyReferences` каждого
слоя-иконки), только чтение, без правок.

## Метод

1. На странице `Components` найдены все слои с именами из набора `icon`,
   `icon-left`, `icon-right`, `leading-icon`, `trailing-icon`, `media`,
   `indicator`, `mark` (без учёта регистра/дефисов) — 475 узлов.
2. Для каждого — владелец (`COMPONENT_SET`, либо `COMPONENT`, если он не внутри
   сета, по правилу: у варианта свойства не читаем, поднимаемся к сету).
3. Для каждого слоя-иконки — `componentPropertyReferences.mainComponent`
   (Instance swap) и `.visible` (Boolean), с именем свойства, если оно есть.
4. Слои, найденные внутри **чужого** вложенного инстанса (например, иконка
   `Select / Item` внутри `Select`, или `Toggle` внутри `Toggle Group`) — не
   считаются отдельной находкой, а помечены как переиспользование; ответственный
   компонент указан отдельно.
5. `Progress → indicator` — ложное срабатывание: это слой заливки прогресс-бара,
   не иконка. Исключён из таблицы.

**Главный результат: Instance swap = ❌ нет везде, без единого исключения.**
Ни один слой-иконка ни в одном компоненте файла не подключён к свойству типа
`INSTANCE_SWAP` на корне. Это значит: на канвасе нельзя выбрать компонент (Button,
Alert, Select/Item и т.д.) и сменить глиф иконки через панель `Properties` — для
этого всегда нужно нырять в сам вложенный инстанс иконки и менять его локально.
`INSTANCE_SWAP`-свойство `glyph` **есть**, но только на самом `Icon base`
(`115:5`) и работает лишь при прямом выборе этого вложенного слоя — наружу, на
корень Button/Alert/Select/Item/Card, оно не прокинуто.

### Про Button — сверка с вашим скриншотом

«нет/нет» подтверждается **только для варианта `Size=icon`** (кнопка-иконка без
подписи): там нет ни instance swap, ни boolean — иконка жёстко зашита и всегда
видима. Для обычных кнопок с подписью (`Size=md/sm/lg`) boolean **есть**
(`Icon left#87:181` / `Icon right#87:182` — это управляет показать/скрыть), просто
instance swap (выбор какая иконка) — везде нет. Если скриншот был снят на
кнопке-иконке — цифры сходятся; если на кнопке с текстом — там «нет/да», не «нет/нет».

## Что не трогал (как и просили)

`Select / Item → indicator` — НЕ баг с пустым слоем (это была ошибка метода в
первой версии отчёта). Реальная картина: внутри `indicator` есть скрытый `Icon`
(глиф `li:check`), видимость которого управляется `Selected#241:7` — корректно
работает как «есть/нет чекмарка». Единственное ограничение — какой именно глиф
(не обязательно чекмарк) показывать, свойством не выбрать; это общее для всего
файла ограничение (см. «Главный результат» выше), а не локальный баг этого
компонента. Никаких правок не вносил.

## Миграция Button: INSTANCE_SWAP для icon-left/icon-right (2026-10-22)

По отдельному запросу — только для **Button** (11-й компонент из списка выше по-прежнему
без `INSTANCE_SWAP` на корне не трогали; остальные 10 вне рамок этой задачи).

### Что сделано

Все 200 вариантов Button (`87:298`): слои `icon-left`/`icon-right` заменены с
плоской невидимой обёртки (`Icon/Size=16` → вложенный `Icon base` → глиф, два
уровня вложенности, `INSTANCE_SWAP` недоступен снаружи) на **прямые инстансы
`Icon base` (`115:5`) с `isExposedInstance=true`**. При выборе инстанса Button в
Figma это даёт отдельную секцию в панели Properties по имени слоя (`icon-left` /
`icon-right`) с полем «Glyph» — то, ради чего всё затевалось (вариант «б» из
исходного обсуждения; плоское «Icon left» без обёртки невозможно, это принято
заранее).

Пакеты: `primary/md/default` (пилот, 1 вариант) → md+sm (99) → lg (50, с
осознанным увеличением иконки 16→20px) → `Size=icon` (50). Заливка каждого слота
переносилась явной привязкой к той же Variable, что была у слота до миграции
(см. ниже почему это стало отдельным шагом).

### Баги, найденные и исправленные по ходу

1. **Заливка не наследуется при `createInstance()` + `INSTANCE_SWAP`.** Новый
   вложенный инстанс глифа подхватывает свой собственный дефолтный fill-токен
   компонента (`li:plus`/`li:arrow-right` их мастер-компонента), а не токен, что
   был у заменяемого слота. Без явного переноса все иконки Button слились бы в
   2-3 дефолтных цвета вместо персональных per-variant токенов (`on-primary`,
   `on-danger`, `outline`/`ghost`→`on-surface` в default и чуть темнее в
   hover/pressed, и т.д.). Исправлено явной привязкой через
   `figma.variables.setBoundVariableForPaint` сразу в скрипте миграции (для
   md+sm и `Size=icon` — отдельным проходом постфактум, для `lg` — уже внутри
   самого скрипта миграции). Проверено: смена глифа **не замораживает** цвет —
   после смены глифа цвет по-прежнему корректно следует за `Variant`/`State`
   (проверено на одноразовом тестовом инстансе: `primary→outline→ghost` и смена
   `State`, заливка на каждом шаге сверена со снимком).
2. **Точечный оверрайд заливки на `310:771`** (production-инстанс в Playground,
   на котором тестировался шаг 2) — побочный эффект ручной проверки смены глифа
   через drill-in: Figma заморозила тогдашнее (ещё не исправленное) значение
   заливки как персональный оверрайд инстанса. Найден полной сверкой всех 110
   инвентаризованных инстансов, исправлен той же привязкой к `VariableID:7:17`.
   `icon-right` на этом же инстансе не был затронут.
3. **Оверрайд глифа `action` в Card (`410:451`) потерян при миграции
   `ghost/Size=icon/State=default`.** Единственный реальный, заранее
   существовавший оверрайд во всём файле (`li:settings` вместо дефолтного
   `li:plus`, см. инвентаризацию ниже) — подход «удалить старый слот, создать
   новый» рвёт привязку даунстрим-оверрайдов, которые Figma хранит по
   внутреннему id узла внутри компонента: старый узел удалён, новый получил
   новый id, оверрайд осиротел и откатился к дефолту. Восстановлен через
   `setProperties({'glyph#115:0': '113:34'})` на самом инстансе `action`;
   заливка на нём и так шла (и продолжает идти) от токена `ghost`, персонального
   оверрайда заливки там не было и не появилось.

### Проверки состояния (обе пройдены)

- **Цвет следует за вариантом после смены глифа.** Одноразовый инстанс,
  мигрированный `primary/md`: Boolean включает иконку → смена глифа через
  drill-in (эквивалент поля «Glyph» в панели) → `Variant: primary → outline →
  ghost` + смена `State` (`default→hover`, `default→pressed`) — заливка на
  каждом шаге сверена с ожидаемым токеном варианта из снимка, 0 расхождений,
  глиф не сбрасывается. Тестовый инстанс удалён.
- **Глиф/размер/заливка переживают переключение `Size: md ↔ lg` (16↔20px).**
  Тот же метод, одноразовый инстанс: смена глифа на `md` → `lg` → обратно на
  `md`. Глиф устойчив, заливка не меняется (`VariableID:7:17` на всех трёх
  шагах), размер корректно переключается 16→20→16. Тестовый инстанс удалён.

потому что нечему было теряться.

  `glyphKey` 2026-10-22) против текущего состояния файла: **0 расхождений** —
